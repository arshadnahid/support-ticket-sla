# 12. Search and Filtering

Assessment section **12**: search and filter tickets by ticket ID, keyword, status, priority, category, assigned
agent, customer, created date and SLA status. There is no new endpoint: the ticket list endpoints take query parameters.

## Step 1 | Decisions at a glance

| Question | Decision |
|---|---|
| Where | The same three list endpoints: `GET /api/tickets`, `/api/tickets/active`, `/api/tickets/resolved` |
| How filters combine | All filters are optional and combine with **AND** |
| Keyword search | `LIKE` on ticket number, subject and description |
| Who sees what | Unchanged: filters run **after** the visibility rules, so they can only narrow a list |
| Pagination | `next_page_url` and `prev_page_url` keep the filters |
| Code shape | One request class validates, one DTO (`TicketListFilters`) carries the values, one repository method applies them |

## Step 2 | Parameters

| Parameter | Meaning | Rules |
|---|---|---|
| `q` | Keyword: matches anywhere in the ticket number, subject or description. Not case sensitive | 2 to 100 characters |
| `number` | Exact ticket number (`TKT-2026-000001`), not case sensitive | up to 32 characters |
| `status` | `open`, `in_progress`, `waiting_for_customer`, `resolved`, `closed` | one of these |
| `priority` | `low`, `medium`, `high`, `critical` | one of these |
| `category_id` | Category (id from `GET /api/categories`) | must exist |
| `assigned_to` | Tickets assigned to this agent (user id) | must exist; not together with `unassigned` |
| `unassigned` | `true` = tickets nobody has taken yet | `true/false/1/0`; not together with `assigned_to` |
| `customer_id` | Tickets created by this customer (user id) | must exist |
| `created_from` | Created on or after this day | `YYYY-MM-DD` |
| `created_to` | Created on or before this day, **the whole day included** | `YYYY-MM-DD`, not before `created_from` |
| `sla` | `within`, `approaching`, `breached` (see [8.sla.md](8.sla.md)) | active tickets only |
| `sort` | `sla_deadline`, `created_asc`, `created_desc` | default: newest first (`/active`: earliest deadline first) |
| `page`, `per_page` | Pagination | `per_page` 1 to 100, default 15 |

A bad value returns **422** with the field name (for example `priority=urgent`, `created_from=10/01/2026`, `category_id=99999`).

## Step 3 | How the filters behave

- **Keyword** looks for the text *anywhere* in the number, subject or description, so `q=password`, `q=000031` and `q=reset my` all work.
  The characters `%` and `_` (and `!`) are searched for as written; they are **not** wildcards, so `q=50%` finds "50%" and not every ticket.
- **Ticket ID** has two forms: `number=` is an exact match (any letter case), and `q=` finds it by part of the number.
- **Dates** are whole days in the application timezone (UTC). `created_from=2026-10-01&created_to=2026-10-10` includes a ticket
  created at 2026-10-10 23:59:59. Tickets created in the "business day" of another timezone can therefore land a few hours either side.
- **SLA status** uses the stored deadline and warning times, so it is an indexed comparison, not a calculation per ticket.
  It lists **active** tickets only; a resolved ticket is never "breached" in this list.
- **Combining**: `?q=vpn&priority=critical&assigned_to=3&status=in_progress` returns tickets that match **all** of them.
- **Sorting** works together with any filter, and with the scope of the endpoint (`/active` still only lists active tickets).

## Step 4 | Access rules are never widened

A filter is applied on top of the ticket-visibility rule (`Ticket::visibleTo`), never instead of it:

| Role | Can see | So filtering by... |
|---|---|---|
| Customer | own tickets | `customer_id=<someone else>` or someone else's `number` returns nothing |
| Agent | tickets assigned to them + the unassigned queue | `assigned_to=<another agent>` returns nothing |
| Admin | everything | every filter works as written |

This is covered by a test that tries to reach other people's tickets through each filter.

## Step 5 | How it is built

```
ListTicketsRequest   validates every parameter, builds a TicketListFilters object
TicketController     passes it to TicketService::list()
TicketRepository     Ticket::visibleTo($user)          <- who may see what
                     applyFilters(...)                 <- narrows (AND)
                     applyScope(...)                   <- active / resolved / all, and the sort
                     paginate()->withQueryString()
```

Adding a filter later means: one rule in the request, one field in the DTO, one line in `applyFilters`, one Swagger parameter.

**Cost.** Equality filters (`status`, `priority`, `category_id`, `assigned_to`, `customer_id`, dates, SLA) use the existing indexes
or small scans. The keyword search is a `LIKE '%text%'`, which cannot use an index, so it scans the (already visibility-filtered)
tickets. That is fine for thousands of tickets; for much more, see the limits.

## Step 6 | Examples

```
GET /api/tickets?q=login
GET /api/tickets?number=TKT-2026-000031
GET /api/tickets?status=open&priority=high&sort=sla_deadline
GET /api/tickets?assigned_to=3&status=in_progress
GET /api/tickets?unassigned=true&priority=critical
GET /api/tickets?customer_id=5&created_from=2026-10-01&created_to=2026-10-31
GET /api/tickets?sla=breached&sort=sla_deadline
GET /api/tickets/resolved?q=refund&category_id=2
```

Swagger: every parameter is documented on the three list endpoints. Bruno: `list tickets` documents them all, `search tickets` is a
ready example, and `list sla breached tickets` covers the SLA filter.

## Step 7 | Tests and how it was checked

`TicketSearchTest` (15 tests):

| Covered |
|---|
| Keyword matches subject, description (any case) and part of the number |
| `%` and `_` in the keyword are literal, not wildcards |
| Keyword length validated; exact number lookup ignores case, unknown number gives an empty result |
| Each filter on its own: status, priority, category, assigned agent, `unassigned`, customer, created date (whole days, both ends included), SLA state |
| Bad values return 422 (priority, category, `assigned_to` with `unassigned`, `unassigned=maybe`, date format, `created_to` before `created_from`) |
| Filters combine with AND; search works on `/active` and `/resolved` and together with `sort` |
| **Filters cannot reveal tickets the user may not see** (customer by `customer_id` / `number`, agent by `assigned_to`) |
| Pagination links keep the filters |
| The number of database queries does not grow with the number of tickets returned |

**Beyond the test suite:** the `LIKE ... ESCAPE '!'` query was also run against the real MySQL database (the tests use SQLite) and executes
correctly. Search speed was **not measured on a large data set**.

## Step 8 | Decisions, assumptions and limits

1. **Keyword search covers number, subject and description only**, not reply text or file names. Searching replies would have to repeat the
   rule that hides internal notes from customers, so it was left out.
2. **`LIKE` search, not full-text.** No stemming, ranking or typo tolerance. For a large system, a MySQL `FULLTEXT` index or a search
   engine would replace `matchKeyword()` without changing the API.
3. **One value per filter.** For example one status at a time, not `status=open,in_progress` (the `/active` list already means "not finished").
4. **Customer and agent are filtered by id**, not by name or email. A UI would use its own lists of users to fill these in.
   There is no endpoint that lists users yet.
5. **Dates are UTC days.**
6. **An empty result returns HTTP 404** with `"data": []`, as the existing lists already do. The pagination block is still present.
7. **Filtering by a user or category that does not exist returns 422**, which catches typos instead of silently returning an empty list.
