# 8. SLA Management

Assessment section **8**: every ticket has a resolution SLA based on its priority, and the app can tell
which tickets are **within SLA**, **approaching breach** or **breached**. The rules are configuration, not code.

Related: how the deadline is calculated from business hours is in [9.business-hours.md](9.business-hours.md);
what happens to tickets that approach or pass the deadline is in [10.sla-escalation.md](10.sla-escalation.md).

## Step 1 | Decisions at a glance

| Question | Decision |
|---|---|
| Where the SLA rules live | `config/sla.php` (values overridable in `.env`). Nothing about hours or priorities is hard-coded elsewhere |
| What the SLA measures | Time to **resolve**, in **business hours** (see 9) |
| Default hours | Low 48, Medium 24, High 8, Critical 2 (the assessment example) |
| Deadline | Calculated **once** when the ticket is created and stored in `tickets.due_at` |
| Approaching | A second stored time, `sla_warning_at`: when 80% of the SLA has been used |
| State | A plain comparison of "now" with those two stored times |
| Who sees the state | Staff. Customers see `due_at` but not the SLA block |

## Step 2 | Configuration: changing the rules

Everything is in `config/sla.php`:

```php
'resolution_hours' => ['low' => 48, 'medium' => 24, 'high' => 8, 'critical' => 2],
'warning_percent'  => 80,
'business_hours'   => [ 'timezone' => 'Asia/Dhaka', 'days' => [0,1,2,3,4], 'start' => '09:00', 'end' => '18:00', 'holidays' => [] ],
```

Each value can also be set in `.env` (`SLA_HOURS_CRITICAL=1`, `SLA_WARNING_PERCENT=75`, ...; list in `.env.example`).

**Changing a rule touches no code.** Edit the config, then run:

```
php artisan tickets:recalculate-sla
```

which re-applies the rules to tickets that are still open (counting from each ticket's creation time). Resolved and closed
tickets keep the deadline they had, because the promise made at the time does not change after the fact. Tickets created after
the change use the new rules automatically.

Adding a new priority means adding it to the `TicketPriority` enum and one line to `resolution_hours`. An unknown priority falls
back to the Medium hours instead of failing.

## Step 3 | What is stored

Migration `add_sla_columns_and_activities` (on `tickets`):

| Column | Meaning |
|---|---|
| `due_at` | The resolution deadline (this column already existed, reserved for this module) |
| `sla_warning_at` | When the ticket starts to count as "approaching" |
| `escalation_level` | 0 not escalated, 1 escalated as approaching, 2 escalated as breached (see 10) |
| `escalated_at` | When it was last escalated |

**Why store both times instead of calculating on read.** With `due_at` and `sla_warning_at` saved, "which tickets are breached"
is `WHERE due_at < now()`, an ordinary query that can use an index (`(status, due_at)` and `(status, sla_warning_at)`), and
nothing needs business-hours maths when a list is shown. The trade-off is that the dates must be refreshed when the rules
change; that is what `tickets:recalculate-sla` is for.

## Step 4 | The three states

`SlaService::stateOf()` (enum `SlaState`):

| State | Active ticket (open, in progress, waiting for customer) | Resolved or closed ticket |
|---|---|---|
| **Within SLA** (`within`) | now is before `sla_warning_at` | finished at or before `due_at` |
| **Approaching SLA breach** (`approaching`) | now is at or after `sla_warning_at`, and not past `due_at` | never |
| **SLA breached** (`breached`) | now is after `due_at` | finished after `due_at` |

Details:
- Exactly at the deadline is **not** yet breached; one second later is.
- A finished ticket is judged by when it was finished (`resolved_at`, else `closed_at`), so a ticket resolved on time stays
  "within SLA" forever instead of turning "breached" as the clock keeps running.
- A ticket without a deadline (created before this module existed, until `tickets:recalculate-sla` is run) has no state (`null`).

Example, Critical (2 business hours) created Monday 10:00: warning at 11:36 (80% = 96 minutes), deadline 12:00.

## Step 5 | When deadlines are set and changed

| Event | What happens |
|---|---|
| Ticket created | `due_at` and `sla_warning_at` are calculated from the creation time and saved with the ticket |
| Priority changed on an active ticket | Recalculated **from the creation time** with the new priority. Raising the priority can make it overdue at once; lowering it gives more time. The escalation level goes down if the new deadline is further away (so it can escalate again), never up |
| Priority changed on a finished ticket | Deadline unchanged |
| Status changes | The deadline does not change (see limits) |
| Rules changed in config | `php artisan tickets:recalculate-sla` |

## Step 6 | API

No new endpoints. The existing ones are extended.

**Ticket response**, for staff only (admin and agent):

```json
"due_at": "2026-10-18T04:00:00.000000Z",
"sla": {
  "state": { "value": "approaching", "label": "Approaching SLA breach" },
  "warning_at": "2026-10-12T05:36:00.000000Z",
  "business_minutes_remaining": 20,
  "escalation_level": 0,
  "escalated_at": null
}
```

`business_minutes_remaining` counts working minutes only (nights, weekends and holidays do not reduce it) and is `null` once the ticket
is resolved or closed. Customers get `due_at` but no `sla` block.

**List filter:** `GET /api/tickets?sla=within|approaching|breached` returns **active** tickets in that state (invalid value is 422).
Combine it with `sort=sla_deadline` for "most urgent first", for example `?sla=breached&sort=sla_deadline`. The filter also works
on `/api/tickets/active`.

Swagger: `sla` parameter and the `sla` object in the Ticket schema. Bruno: `list sla breached tickets`.

## Step 7 | Tests

`TicketSlaTest` (14 tests):

| Covered |
|---|
| The assessment example: Critical created Thursday 5 PM is due Sunday 10 AM, not 7 PM |
| Each priority gets its own deadline; changing `resolution_hours` or the business hours in config changes the result with no code change |
| Warning time is 80% of the SLA in working time (36 minutes into Sunday, not wall-clock) |
| Within, then approaching, then breached; exactly at the deadline is still approaching |
| The clock does not run on the weekend |
| Finished tickets are judged by their finish time; a ticket without a deadline has no state |
| Remaining time is in working minutes |
| Staff see the `sla` block, customers do not |
| The `sla` list filter, including that closed tickets are never "breached" in it |
| Priority change recalculates from creation time; a finished ticket keeps its deadline |

## Step 8 | Decisions, assumptions and limits

1. **The SLA clock never pauses.** A ticket in `waiting_for_customer` still counts down. Pausing while waiting on the customer is
   common in real products; it would need a "paused since" time and an adjusted deadline. Not requested, so not built.
2. **One SLA per priority.** No per-category, per-customer or per-plan SLAs.
3. **Resolution time only.** There is no first-response SLA (the `TicketReplied` event is the place to add one).
4. **A reopened ticket keeps its original deadline.** If it was already past it, it is breached again at once.
5. **The warning percentage is global**, not per priority.
6. **Dates are stored in UTC**; only the working day is read in the SLA timezone (see 9).
7. **Seeded demo tickets** get real deadlines from these rules, so the demo data shows a mix of the three states.
