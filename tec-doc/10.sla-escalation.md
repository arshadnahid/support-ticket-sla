# 10. SLA Escalation

Assessment section **10**: tickets that are approaching or have exceeded their SLA are found and escalated automatically.
An escalation here does four things: **marks the ticket as escalated**, **creates a history entry**, **notifies the right people in
the app**, and **sends them an email**.

Builds on [8.sla.md](8.sla.md) (the states) and [9.business-hours.md](9.business-hours.md) (the deadlines).

## Step 1 | Decisions at a glance

| Question | Decision |
|---|---|
| How tickets are found | A command, `tickets:escalate-sla`, scheduled **every minute** |
| Levels | **Two**: approaching (1) and breached (2). Each is escalated **once** per ticket |
| Marking | `tickets.escalation_level` and `escalated_at` |
| History | A row in `ticket_activities` (`sla_warning` or `sla_breached`) written by the system |
| Notification | Email **and** a stored in-app notification (Laravel notifications, queued) |
| Recipients | Approaching: the assigned agent (admins if nobody has it). Breached: the assigned agent **and all admins**. Never customers |
| Event | `TicketSlaEscalated`, so later modules can react without touching this code |

## Step 2 | How it runs

```
every minute (scheduler)
  php artisan tickets:escalate-sla
    find ACTIVE tickets that have reached a level they were not escalated for:
        escalation_level < 2 AND due_at < now          (breached)
     OR escalation_level < 1 AND sla_warning_at <= now (approaching)
    most overdue first, up to SLA_ESCALATION_BATCH (default 200)
    for each: SlaEscalationService::escalate(id)
```

The query uses the stored `due_at` and `sla_warning_at`, so it needs no business-hours maths and can use the `(status, due_at)` and
`(status, sla_warning_at)` indexes. Only tickets with something new to escalate come back, so a busy desk does not re-read the same
tickets every minute.

## Step 3 | What an escalation does

`SlaEscalationService::escalate()` runs in one transaction on the **locked** ticket row:

1. Ignore the ticket if it is resolved or closed (the work is done).
2. Work out its state now. If it is within SLA, or this level (or a higher one) was already escalated, do nothing.
3. Save `escalation_level` (1 or 2) and `escalated_at` on the ticket.
4. Write a history entry in `ticket_activities`: `type` (`sla_warning` / `sla_breached`), a readable `description`
   ("SLA breached: the resolution deadline passed."), `user_id = null` (the system) and `properties` (state, due time, priority, assignee).
5. Fire `TicketSlaEscalated` after the commit.

The listener `NotifySlaEscalation` then sends `TicketSlaEscalatedNotification` (mail + database). The notification is queued, so
a slow mail server never slows the sweep.

A ticket that was never warned (for example the scheduler was off) goes straight to level 2 with a single breach escalation.
A ticket that is warned and later breaches is escalated twice, once for each level.

## Step 4 | Who is notified

| Level | Recipients |
|---|---|
| Approaching | The assigned agent. If the ticket is unassigned, all admins |
| Breached | The assigned agent **and** all admins |

Only **active** users are notified, customers never are (the SLA is internal), and each person gets one notification even if they
are both assignee and admin.

The **email** states the ticket number, subject, priority, deadline (UTC) and assignee. The **in-app** copy is stored in the
`notifications` table with `type`, `ticket_number`, `state`, `message` and `due_at`. In development `MAIL_MAILER=log` writes the
email to `storage/logs/laravel.log`.

## Step 5 | Running it safely

| Concern | How it is handled |
|---|---|
| Notifying twice for the same thing | The level is saved on the ticket and checked under the row lock. Running the sweep again, or twice at the same moment, finds the level already done |
| Two sweeps overlapping | `withoutOverlapping()` and `onOneServer()` on the schedule, and the row lock as the real guarantee |
| The ticket was resolved while the sweep ran | The state is re-read under the lock; finished tickets are skipped |
| Scheduler or queue down for a while | The next run catches up: everything that crossed a level is found by the query. A ticket that crossed both levels meanwhile gets one breach escalation |
| One ticket failing | Each ticket is its own transaction. An error is logged, the sweep carries on with the other tickets, the command reports the failure, and the next run retries that ticket |
| Priority or rules change later | The escalation level is lowered if the new deadline is further away, so the ticket can be escalated again properly (see 8, Step 5) |

## Step 6 | What must be running

| Process | Command | Needed for |
|---|---|---|
| Scheduler | `php artisan schedule:work` (dev) or a cron entry for `schedule:run` every minute (production) | The sweep |
| Queue worker | `php artisan queue:work` | Sending the emails and storing the notifications |

These are the same two processes automatic assignment uses (README section 7). Settings: `SLA_ESCALATION_BATCH`, and the mail settings
(`MAIL_*`) for real email.

Useful commands:

```bash
php artisan tickets:escalate-sla        # run the sweep once by hand
php artisan tickets:recalculate-sla     # after changing config/sla.php
php artisan schedule:list
```

## Step 7 | Tests and how it was checked

`TicketSlaEscalationTest` (16 tests):

| Covered |
|---|
| Past the warning time becomes level 1; past the deadline becomes level 2; within SLA and no-deadline tickets are untouched; resolved and closed tickets are never escalated |
| The history entry (type, system user, state, assignee) |
| **Each level once**: running the sweep three times creates one entry and one notification; warned then later breached gives two entries; never-warned breach gives one |
| `TicketSlaEscalated` event fired once per level |
| Recipients: warning goes to the agent only; breach goes to the agent and every admin; unassigned goes to admins; customers and inactive users never; no duplicates |
| The stored notification and the email subject and content |
| `tickets:recalculate-sla` updates open tickets only, leaves finished ones alone, and lowers the escalation level when the deadline moves away |

**Beyond the test suite:** `php artisan tickets:escalate-sla` was run against the real MySQL database (it escalated 0 tickets, because the
existing demo tickets had no deadlines yet) and the schedule lists it as due every minute. The notification tests use Laravel's fake;
**a real email was not sent and the end-to-end path with a live queue worker was not run**, and the sweep was not load-tested.

## Step 8 | Decisions, assumptions and limits

1. **Escalation does not change the ticket's priority or reassign it.** It flags, records and notifies. Reassigning or raising
   priority automatically can surprise people, so it was left out.
2. **Two levels only.** No further steps such as "notify a manager after 2 more hours".
3. **Admins are the escalation contacts.** There is no per-team manager or on-call list.
4. **The notification inbox is not an endpoint yet.** Notifications are stored (`notifications` table, readable through
   `$user->notifications`), but there is no API to list or mark them read. That belongs with the notifications module (assessment section 11).
5. **The history table is generic** (`ticket_activities`) but only SLA escalations write to it so far, and there is no endpoint to read it yet
   (assessment section 15).
6. **A reopened ticket that was already escalated** keeps its level; it will not be escalated again for the same level.
7. **The sweep is once a minute**, so escalation can be up to about a minute late.
8. **Mail failures are handled by the queue** (3 tries), separately from the sweep.
