## Step 1 | Decisions at a glance

| Question | Decision |
|---|---|
| Attach to what | The ticket itself (`POST /attachments`) **or** a reply / internal note (`attachments[]` on `POST /replies`) |
| Who | Same people as replying: the owning customer, the assigned agent, admins |
| Where files live | A **private** disk (`storage/app/private`), outside the web root |
| Names on disk | Random UUID plus a whitelisted extension. The uploaded name is only a label |
| Limits | 5 files per request, 5 MB each, whitelisted types only |
| Download | Only through an authenticated, authorised endpoint, always as a download |
| Internal notes | Their files are as hidden as the note: 404 for customers |

## Step 2 | Database

Migration `create_ticket_attachments_table`.

| Column | Purpose |
|---|---|
| `uuid` | The **public id** used in URLs (the numeric id is never exposed) |
| `ticket_id` | The ticket |
| `reply_id` | `null` = attached to the ticket; otherwise the reply or note it belongs to |
| `uploaded_by` | Who uploaded it |
| `disk`, `path` | Where the file is. `path` is server-generated and never returned by the API |
| `original_name` | The name shown to users (sanitised) |
| `mime_type`, `size` | Detected from the file's content, not from the client |

## Step 3 | Validation and restrictions

Rules are in one place, `AttachmentRules`, used by every endpoint that accepts files.

| Check | Rule |
|---|---|
| Is it a real upload | `file` |
| Size | `max` 5120 KB (5 MB) per file |
| Count | at most 5 files per request |
| Name | extension must be on the whitelist (`extensions:`) |
| **Content** | the file's real type, sniffed from its bytes, must be on the whitelist too (`mimes:`) |

**Allowed:** `jpg`, `jpeg`, `png`, `gif`, `webp`, `pdf`, `txt`, `log`, `csv`, `docx`, `xlsx`.

**Deliberately not allowed:** `svg` (can carry scripts), `html`/`htm`, `php` and other scripts, `exe`, `sh`,
and archives such as `zip` (can hide anything). Old Office formats (`doc`, `xls`) are left out too because they
can carry macros; the modern formats are accepted.

Because both name and content are checked, **renaming a file does not get it through**: an executable named
`invoice.pdf` fails on content, and `page.html` fails on name.

## Step 4 | Storage

`AttachmentStorage` is the only class that touches files.

- Written to `ticket-attachments/{ticket id}/{uuid}.{ext}` on the private disk.
- The stored name never contains anything the user typed, so path traversal (`../../x`) and overwriting another
  file are impossible. A hostile upload name such as `../../etc/passwd.pdf` is kept only as the label `passwd.pdf`
  (folders and control characters are stripped, length is capped at 150).
- Files are written **before** the database transaction and removed again if the transaction fails or the ticket turns
  out to be closed, so a failed request leaves no orphan files.
- The disk comes from config (`TICKET_ATTACHMENT_DISK`), so moving to S3 later is a configuration change plus the
  usual Laravel filesystem driver. Downloads already go through `Storage::download`, which streams from any disk.

## Step 5 | Secure access

```
GET /api/tickets/{number}/attachments/{id}
  logged in ?                                   no  -> 401
  can the user view this ticket ?               no  -> 403
  does {id} belong to THIS ticket ?             no  -> 404   (scoped route binding)
  is it on an internal note and user is a customer ?  yes -> 404
  file missing on disk ?                        yes -> 404
  -> stream the file
```

| Protection | How |
|---|---|
| No direct URL | The file is not on a public disk; there is no `/storage/...` link |
| Authentication and authorisation | Same JWT and `view` policy as the ticket itself |
| No guessing | Ids are UUIDs, and a customer gets the same 404 for "hidden" and "does not exist" |
| No cross-ticket access | `scopeBindings()`: an id from ticket A requested through ticket B is 404 |
| No stored XSS | Always `Content-Disposition: attachment`, never inline, plus `X-Content-Type-Options: nosniff` |
| Right type header | `Content-Type` is the type detected from the file content, not what the client claimed |
| No caching of private data | `Cache-Control: private, no-store` |

**Browser note:** the endpoint needs the `Authorization` header, so a plain `<a href>` will not work. A front end fetches
it with the token and saves the response (Bruno: "Save response"). A signed temporary URL would be the alternative
if a plain link were required.

## Step 6 | Endpoints

| Method and path | Who | Success | Failures |
|---|---|---|---|
| `POST /api/tickets/{number}/attachments` `files[]` (multipart) | Owner, assigned agent, admin | 201 | 401, 403, 404, **409** (closed), 422 |
| `POST /api/tickets/{number}/replies` with `attachments[]` (multipart) | See [6.conversation.md](6.conversation.md) | 201 | as above |
| `GET /api/tickets/{number}/attachments` | Anyone who can view the ticket | 200 | 401, 403, 404 |
| `GET /api/tickets/{number}/attachments/{id}` | Anyone who can view the ticket (and the file) | 200 file | 401, 403, **404** |

Each attachment in a response:

```json
{
  "id": "5f0e4c1a-6b1e-4f7e-9a3c-2d8b7c1e9f10",
  "filename": "screenshot.png",
  "mime_type": "image/png",
  "size": 48213,
  "reply_id": null,
  "uploaded_by": { "id": 5, "name": "Customer One" },
  "created_at": "2026-10-12T09:30:00.000000Z",
  "download_url": "http://support-ticket-sla.test/api/tickets/TKT-2026-000001/attachments/5f0e4c1a-..."
}
```

Swagger: tag **Attachments** (multipart request bodies are documented). Bruno: folder **Conversation**
(`upload files to ticket`, `list attachments`, `download attachment`, `reply with files`). Put a real file path in the
file row (a tiny `sample.pdf` is included).

## Step 7 | Configuration

`config/tickets.php` (`attachments`), overridable in `.env`:

| Variable | Default | Meaning |
|---|---|---|
| `TICKET_ATTACHMENT_DISK` | `local` (private) | Filesystem disk for the files |
| `TICKET_ATTACHMENT_MAX_KB` | `5120` | Max size of one file |
| `TICKET_ATTACHMENT_MAX_FILES` | `5` | Max files per request |

The whitelist is `attachments.types` in the same file. PHP's own limits (`upload_max_filesize`, `post_max_size`)
must be at least as large as the limit above, or PHP rejects the upload before Laravel sees it.

## Step 8 | Tests and how it was checked

`TicketAttachmentTest` (18 tests), using a fake disk:

| Covered |
|---|
| Customer attaches to own ticket; response never contains the storage path |
| Stored under a random UUID name; a `../../etc/passwd.pdf` upload cannot escape |
| Assigned agent and admin can attach; other customers and agents cannot |
| Closed ticket: 409 and **nothing left on disk** |
| Rejected: `.exe`, `.html`, `.svg`, `.php`, `.zip`, `.sh`; an executable renamed to `.pdf` is rejected by content |
| Size limit (over fails, exactly at the limit passes), count limit, at least one file required |
| Files sent with a reply; a failed reply leaves no orphan files |
| Download: correct bytes, `attachment` disposition, `nosniff`, `no-store`; 401 for guests, 403 for outsiders |
| An id cannot be fetched through a different ticket (404); unknown id is 404; the disk is not public |
| **Files on internal notes are hidden from customers** in the list, the conversation and the direct download (404), but staff can still get them |
| A customer cannot attach files to an internal note (403, nothing stored) |

**Beyond the test suite:** the validation rules were run against real files, not fakes. Passed: a real PDF, a real
PNG, a CSV, a log file and a genuine Word `.docx` (detected as `application/vnd.openxmlformats-officedocument.wordprocessingml.document`).
Rejected: an `.exe`, a `.zip`, an `.html`, and an HTML file renamed `page.pdf` (caught by its content). **Not checked
against a real `.xlsx`** (none was available), and not against a very large upload through a real web server.

## Step 9 | Decisions, assumptions and limits

1. **No virus scanning.** The whitelist and content check stop disguised executables and web content, but they do not
   detect malware inside a valid PDF or Office file. A scanner (for example ClamAV on upload) would be the next step.
2. **No deleting or replacing attachments.** Not requested; it would need a policy and a clean-up of the file on disk.
3. **No per-ticket total size or file count limit.** Only per request. A quota would be a small addition.
4. **Images are not resized or re-encoded**, and EXIF data (such as location) is kept.
5. **`txt`, `csv` and `log` share one detected type** (`text/plain`), so these three are told apart by the name only.
6. **Office files are accepted as-is.** `docx` and `xlsx` are modern formats without macros, but a file can still contain
   links or embedded content. They are only ever served as downloads.
7. **Downloads need the token** (see the browser note in Step 5).
8. **Local disk by default.** Fine for one server; for several servers use a shared disk such as S3.
