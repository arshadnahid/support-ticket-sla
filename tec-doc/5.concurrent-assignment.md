### Flow 1 | Two agents accept the same unassigned ticket at the same time

```
 Ticket TKT-2026-000031 is unassigned.  Agent A and Agent B both press Accept.

 Agent A                                         Agent B
 BEGIN                                           BEGIN
 SELECT ticket FOR UPDATE   -> gets the lock     SELECT ticket FOR UPDATE   -> WAITS
 assigned_to is null  -> OK
 UPDATE assigned_to = A
 COMMIT                     -> lock released     (lock granted, reads the NEW row)
                                                 assigned_to = A  -> not null
                                                 ROLLBACK, 409
 200 "Ticket accepted"                           409 "already assigned to another agent"

 Result: the ticket belongs to A. B is told clearly. No overwrite, no double assignment.
```

Which agent "wins" is whoever the database lets take the lock first. It is not decided by the
application, and it does not matter: exactly one succeeds.

### Flow 2 | Different paths at the same time

The same lock covers every way of assigning, so mixed races are safe too.

| Happening at the same time | Outcome |
|---|---|
| Agent A accepts and Agent B accepts | One wins; the other gets **409** (Flow 1) |
| An agent accepts and the **auto-assign job** runs | Whoever locks first wins. If the job wins, the agent gets **409** (or 200 if the job happened to pick that very agent). If the agent wins, the job sees an assignee and quietly does nothing |
| Two auto-assign jobs on the same ticket | The second sees an assignee and does nothing (and the job is unique per ticket anyway) |
| An admin assigns and an agent accepts | They run one after the other. If the agent is first, the admin's assign then **replaces** the assignee (admins may reassign). If the admin is first, the agent gets **409** |

Measured on real MySQL with parallel processes: 8 agents accepting at once (10 rounds), and 4 agents
plus 2 auto-assign jobs on the same ticket (6 rounds). See Step 1 and Step 3 for the numbers.

## Step 1 | Concurrent accept: the lock

### The problem (assessment section 5)

Two agents press **Accept** on the same unassigned ticket at about the same moment. Each request
loaded the ticket a few milliseconds earlier, and both saw `assigned_to = null`.

Without protection, both do "check it is free, then write my name". Both checks pass, both writes
succeed, the second silently overwrites the first, and **both agents are told they own it**.

### The solution: `lockForUpdate` (as suggested)

```php
DB::transaction(function () use ($ticket, $agent) {
    $locked = $this->tickets->lockForUpdate($ticket->id);   // SELECT ... FOR UPDATE

    $this->guardAssignable($locked);                        // not resolved/closed

    if ($locked->assigned_to === $agent->id) return $locked;           // already mine: harmless
    if ($locked->assigned_to !== null) throw TicketAssignmentException::alreadyAssigned();

    $this->applyAssignment($locked, $agent, AssignmentMethod::Accepted, $agent);
    return $locked;
}, attempts: 3);
```

What happens with two agents, A and B:

```
 time   Agent A                              Agent B
  1     BEGIN                                BEGIN
  2     SELECT ... FOR UPDATE   (gets lock)  SELECT ... FOR UPDATE   (WAITS)
  3     assigned_to is null -> write A
  4     COMMIT (lock released)               (gets lock now)
  5                                          assigned_to = A  -> throw 409
  6     200 "Ticket accepted"                409 "already assigned to another agent"
```

**The key point:** the decision is made from the row read **after** taking the lock, never from the
copy loaded earlier in the request. That is why B is refused even though B's earlier copy said
"unassigned". A test proves exactly this (`test_the_loser_of_a_race_is_decided_by_the_locked_row_not_a_stale_copy`).

**Also handled**
- *Double click:* the same agent accepting twice gets 200 the second time, with one event only.
- *Deadlocks:* `attempts: 3` retries the transaction if MySQL picks it as a deadlock victim.
- *Lock order:* always ticket first, then agents by id. A fixed order means two transactions can
  never wait on each other in a circle.

### Why a lock and not another approach

| Option | Verdict |
|---|---|
| **`lockForUpdate` (chosen)** | Simple to reason about. Lets us also check the status, write the timestamps and fire the event in one transaction |
| Atomic `UPDATE ... WHERE assigned_to IS NULL`, check rows affected | Also correct and lock-free from the app's point of view; fine alternative, but the status check, event and "same agent again" case need extra queries |
| Version column (optimistic locking) | Needs retry logic on conflict. Better when conflicts are rare and holding locks is costly; here conflicts are the expected case |
| Check in PHP only | **Wrong.** This is the bug the lock exists to prevent |

### Proof: real MySQL, 8 agents firing at the same instant

A script starts 8 PHP processes that all wait for the same clock time and then accept the same ticket.

| Run | Rounds | Result per round |
|---|---|---|
| **Control: read, check, write, no lock** | 4 | **8 winners every round.** All 8 agents were told "success"; the database kept only the last write |
| **`TicketAssignmentService::accept` with the lock** | 10 | **Exactly 1 winner, 7 clean 409s, 0 errors, 0 deadlocks**, every round |

(SQLite ignores row locks, so this can only be checked on MySQL. It cannot be a normal PHPUnit test.)

## Step 2 | The other assignment paths use the same lock

`autoAssign()` and `assign()` also start with `lockForUpdate` on the ticket, so every mixed race in Flow 2
is safe. Automatic assignment additionally locks the available agents' rows, always ticket first, then
agents ordered by id. Two jobs therefore cannot read the same workload numbers and pick the same agent,
and the fixed lock order means two transactions cannot wait on each other in a circle. Details of the
strategy: [4.ticket-assignment.md](4.ticket-assignment.md#step-5--automatic-assignment).

## Step 3 | Tests and how it was checked

**Automated** (`tests/Feature/Ticket/TicketAssignmentTest.php`):

| Test | Proves |
|---|---|
| `test_second_agent_accepting_the_same_ticket_gets_409_and_does_not_take_it` | Second agent gets 409, the first keeps the ticket |
| `test_the_loser_of_a_race_is_decided_by_the_locked_row_not_a_stale_copy` | The loser holds an old "unassigned" copy and is still refused |
| `test_accepting_a_ticket_twice_is_harmless` | Same agent twice gives 200 and one event |

**Beyond the test suite (real MySQL):**

1. **Concurrency:** 8 simultaneous accepts, with and without the lock (Step 1).
   Then a mixed race: 4 agents accepting plus 2 automatic-assignment jobs on the **same ticket**, 6
   rounds. Every round ended with one assignee, **0 errors**, and every reported winner matched the
   owner in the database. In 2 rounds the job and an agent both reported success; in both cases it
   was the **same agent** (the job picked them, then their own accept was the harmless "already yours"
   case), so nothing was assigned twice. Admin-versus-agent races follow from the same lock but were
   not load-tested.

SQLite ignores row locks, so a real race can only be checked on MySQL and cannot be a normal PHPUnit test.
