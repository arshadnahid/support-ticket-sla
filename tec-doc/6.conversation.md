## Step 1 | Decisions at a glance

| Question | Decision |
|---|---|
| Reply vs note | One table, `ticket_replies`, with an `is_internal` flag |
| Who may reply | The customer who owns the ticket, the **assigned** agent, admins |
| Who may write an internal note | The assigned agent and admins. A customer who sends `is_internal: true` gets **403** (never a silent public reply) |
| Who sees internal notes | Staff only (admins, the assigned agent, any agent while the ticket is unassigned) |
| Closed tickets | No new replies or notes: **409** |
| Resolved tickets | Still accept replies (a customer can say "it came back") |
| Reading | Oldest first, paginated (`page`, `per_page`) |

## Step 2 | Database

Migration `create_ticket_replies_table`.

| Column | Purpose |
|---|---|
| `ticket_id` | The ticket (deleted with it) |
| `user_id` | The author |
| `body` | The text (max 10,000 characters) |
| `is_internal` | `true` = internal agent note |

Index `(ticket_id, is_internal, id)` serves the only query there is: one ticket's conversation, oldest
first, with or without notes.

## Step 3 | Who can do what

Rules live in `TicketPolicy` (`reply`, `addInternalNote`) next to the existing ones.

| Action | Admin | Agent | Customer |
|---|---|---|---|
| Read the conversation | yes | assigned to them, or unassigned | own tickets |
| See internal notes | yes | yes (same tickets) | **never** |
| Reply | any ticket | only tickets assigned to them | own tickets |
| Add an internal note | any ticket | only tickets assigned to them | **no (403)** |

An agent must **accept** an unassigned ticket (see [4.ticket-assignment.md](4.ticket-assignment.md)) before
replying. Closed tickets are refused by the service with 409 (the check runs on the locked row, so a reply
cannot slip in while another request is closing the ticket).

## Step 4 | Internal notes: the customer never sees them

"Never" is enforced in one place rather than remembered in every endpoint:

1. **One query scope.** `TicketReply::visibleTo($user)` adds `WHERE is_internal = false` unless the user is staff.
   The repository applies it to every read of replies, so no endpoint can forget it.
2. **Files follow the note.** `TicketAttachment::visibleTo()` hides files attached to an internal note by the same rule
   (see [7.attachments.md](7.attachments.md)).
3. **Not filtered after the fact.** Hidden notes are never loaded into the response, so they cannot leak through a
   resource, a count or an error message. A ticket that only has internal notes looks exactly like an empty one to the customer.
4. **No way to create one by accident.** Only staff pass the `addInternalNote` policy check.
5. **Events.** `TicketReplied` carries `$reply->is_internal`; the future notification module must not email notes to customers.

Tests assert on the raw response body (the note text must not appear anywhere), not just on the JSON fields.

## Step 5 | Endpoints

| Method and path | Who | Success | Failures |
|---|---|---|---|
| `GET /api/tickets/{number}/replies` `?page&per_page` | Anyone who can view the ticket | 200 | 401, 403, 404 (ticket missing, or nothing visible yet), 422 |
| `POST /api/tickets/{number}/replies` | See Step 3 | 201 | 401, 403, 404, **409** (closed), 422 |

`POST` body (JSON, or `multipart/form-data` when sending files):

| Field | Rules |
|---|---|
| `body` | required, text, max 10,000 |
| `is_internal` | optional boolean. In a multipart form `true`/`false`/`1`/`0` all work |
| `attachments[]` | optional files, see [7.attachments.md](7.attachments.md) |

A reply looks like:

```json
{
  "id": 7,
  "body": "Please try clearing your cache and sign in again.",
  "is_internal": false,
  "author": { "id": 3, "name": "Agent One", "email": "agent1@example.com" },
  "author_is_staff": true,
  "attachments": [],
  "created_at": "2026-10-12T09:30:00.000000Z"
}
```

`author.email` is shown to staff only (same rule as elsewhere), so customers never see an agent's address.
`author_is_staff` lets a UI label "Support" vs "You" without exposing roles.

Swagger: tag **Conversation**. Bruno: folder **Conversation** (`list replies and notes`, `reply to ticket`,
`add internal note (staff)`, `reply with files`).

## Step 6 | How a reply is saved

```
POST /replies
  validate (body, is_internal, files)
  Gate: is_internal ? addInternalNote : reply            -> 403
  write any uploaded files to private storage            (see 7.attachments.md)
  BEGIN
    lock the ticket row (SELECT ... FOR UPDATE)
    ticket closed ?                                      -> 409, files removed
    insert the reply, insert one attachment row per file
    fire TicketReplied (after commit)
  COMMIT
```

If anything fails after the files were written, they are deleted, so no orphan files are left behind.

`TicketReplied` has no listener yet. The SLA module (first response time) and notifications attach there later
without touching the conversation code.

## Step 7 | Tests

`TicketConversationTest` (16 tests):

| Covered |
|---|
| Customer, assigned agent and admin can reply; other customers, other agents and unaccepted tickets cannot; guests get 401 |
| `body` required and bounded; closed ticket 409; resolved ticket still accepts replies |
| Internal notes: agent and admin can add them, a customer gets 403 and nothing is saved |
| **Customer never receives an internal note** (checked in the raw response body); staff see replies and notes in order |
| A ticket with only notes looks empty to the customer |
| `is_internal` works from a multipart form (`true`), rejects nonsense |
| Only people who can view the ticket can read its conversation; pagination |
| **No query per reply** (the query count stays the same with 1 or 11 replies) |

## Step 8 | Decisions, assumptions and limits

1. **Replies cannot be edited or deleted.** A support conversation is a record; nothing in the assessment asks for editing.
2. **No automatic status change.** A customer reply does not move a `waiting_for_customer` ticket back to `in_progress`,
   and an agent's first reply does not start or stop any SLA clock. Both belong to the SLA module and attach to `TicketReplied`.
3. **Agents must own the ticket to reply.** An agent cannot reply to a ticket nobody has accepted yet.
4. **An empty conversation returns 404** ("not found") with `data: []`, the same behaviour as the ticket lists.
5. **Plain text only.** The body is stored and returned as text. The API does not render HTML, so a front end must escape it when displaying.
6. **Authors are not anonymised.** Customers see the agent's name (not email) on replies.
