# 9. Business Hours

Assessment section **9**: SLA time is only counted inside configurable business hours. The example
in the assessment: Business days Sunday to Thursday, 9:00 AM to 6:00 PM. A Critical ticket (2-hour SLA) created on
Thursday at 5:00 PM must **not** be due at 7:00 PM, because the office closes at 6:00 PM and is shut on Friday and Saturday.

Builds on [8.sla.md](8.sla.md). Escalation is [10.sla-escalation.md](10.sla-escalation.md).

## Step 1 | Decisions at a glance

| Question | Decision |
|---|---|
| Where the calendar lives | `config/sla.php` (`business_hours`), overridable in `.env` |
| Default | Sunday to Thursday, 09:00 to 18:00, timezone `Asia/Dhaka`, no holidays |
| Method | Walk forward through working time, consuming the SLA minutes day by day |
| Outside working time | The clock starts at the next opening |
| Code | One small class, `BusinessHours`, with no knowledge of tickets |

## Step 2 | Configuration

```php
'business_hours' => [
    'timezone' => env('SLA_TIMEZONE', 'Asia/Dhaka'),
    'days'     => [0, 1, 2, 3, 4],        // 0 = Sunday ... 6 = Saturday
    'start'    => '09:00',
    'end'      => '18:00',
    'holidays' => [],                       // '2026-12-16', ...
],
```

`.env`: `SLA_TIMEZONE`, `SLA_BUSINESS_DAYS` (comma separated, `0,1,2,3,4`), `SLA_BUSINESS_START`, `SLA_BUSINESS_END`,
`SLA_HOLIDAYS` (comma separated dates). After a change run `php artisan tickets:recalculate-sla` so open tickets use it.

A calendar with no working days, or closing before opening, is rejected with an error instead of looping forever.

## Step 3 | The approach

A deadline is "start + N working minutes", so the question is how to spend N minutes. `BusinessHours::addMinutes()`:

```
at = start, moved forward to the next opening if the office is closed
repeat:
    left_today = closing time of that day - at
    if remaining <= left_today:  deadline = at + remaining;  stop
    remaining = remaining - left_today
    at = next opening after that closing time        (skips nights, weekends, holidays)
```

"Next opening" is: now, if the office is open; otherwise today's opening time if it is before opening on a working day;
otherwise the opening time of the next working day. That one rule covers a ticket created at night, at the weekend,
or on a holiday.

The reverse question, "how many working minutes until the deadline", uses the same walk (`minutesBetween()`), which is how the
API shows `business_minutes_remaining`. A test checks that the two are inverses of each other.

**Why not just add hours and adjust.** Adding clock hours and then correcting for closing time breaks as soon as an SLA spans
more than one day (48 hours) or a weekend. Walking through the working time handles every case with the same loop.

## Step 4 | Worked examples

Calendar: Sunday to Thursday, 09:00 to 18:00. Dates in the 2026-10 calendar (Thu 15, Fri 16, Sat 17, Sun 18).

| Created | SLA | Deadline | Why |
|---|---|---|---|
| **Thu 17:00** | **2 h** | **Sun 10:00** | 1 h left on Thursday (17:00 to 18:00); Friday and Saturday are closed; the second hour is Sunday 09:00 to 10:00 |
| Mon 10:00 | 2 h | Mon 12:00 | Fits inside the day |
| Mon 16:00 | 2 h | Mon 18:00 | Ends exactly at closing time |
| Mon 06:00 | 2 h | Mon 11:00 | Clock starts at opening, 09:00 |
| Mon 20:30 | 2 h | Tue 11:00 | Clock starts the next morning |
| Fri 10:00 or Sat 23:00 | 2 h | Sun 11:00 | Weekend: clock starts Sunday 09:00 |
| Sun 09:00 | 48 h | next Sun 12:00 | 5 working days x 9 h = 45 h, then 3 h more |
| Thu 17:00, Sunday 18th is a holiday | 2 h | Mon 19th 10:00 | The holiday is skipped like a weekend |

The warning time uses the same calculation with 80% of the minutes. For the first row that is 96 minutes: Thursday 17:00 to 18:00
is 60, the remaining 36 land on Sunday, so the ticket becomes "approaching" at Sunday 09:36.

## Step 5 | Timezones

- Dates are **stored in UTC** (as everywhere in the app) and returned in UTC.
- The configured timezone only decides what "09:00" means. A ticket created at 11:00 UTC on Thursday is 17:00 in Dhaka (UTC+6),
  so it is due Sunday 10:00 Dhaka, which is Sunday 04:00 UTC. A test covers exactly this.
- Daylight saving time is handled by the timezone database for zones that use it.

## Step 6 | Tests

`BusinessHoursTest` (15 tests, no database): the assessment example; inside one day; ending at closing time; created before opening,
after closing and at the weekend; a 48-hour SLA across a weekend; holidays; fractions of a minute; timezone conversion;
`minutesBetween` (including weekends and never negative); `minutesBetween` is the inverse of `addMinutes`; `isOpenAt`;
invalid calendars rejected.

`TicketSlaTest` checks the same through the API (a Critical ticket created Thursday 17:00 Dhaka is due Sunday 10:00 Dhaka) and that
changing the days and hours in config changes deadlines with no code change.

## Step 7 | Decisions, assumptions and limits

1. **One calendar for the whole system.** No per-customer or per-team calendars.
2. **One shift per day, the same hours every working day.** No lunch break, no half days (for example a short Thursday).
3. **Holidays are a list of dates in config.** Changing them needs a config change and a recalculation; there is no admin screen.
4. **Tickets created outside working hours** start counting at the next opening. This is deliberate: customers are not "late" for
   the night, and it matches how the example in the assessment is meant to work.
5. **Calculation walks day by day.** An SLA of a few hundred hours is a few dozen steps. A calendar with no opening for over 400 days
   is rejected with an error.
6. **Sub-minute precision is kept** (the work is done in seconds), so 0.5 minutes works.
