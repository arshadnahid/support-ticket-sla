# 1. Auth Module: Step by Step

This document records, **in the order we built it**, everything done for authentication and
roles, and the reason behind each step.

**Why this module first?** The assessment (section 3, *Roles and Permissions*) needs three roles,
server-side authorization, and agent availability for auto-assignment (section 4). Every later
module (tickets, assignment, replies) depends on knowing *who* the user is and *what they may do*.

## Big picture: what happens to a request

```
Request
  -> throttle:auth   too many attempts?        -> 429   (public routes only)
  -> auth:api        valid token?              -> 401
  -> active          account still enabled?    -> 403
  -> role:...        right kind of user?       -> 403
  -> Controller -> Service -> Repository -> Database
  <- JSON response in one standard format
```

Every response, success or error, uses the same envelope:

```json
{ "data": null, "message": "...", "errors": [], "success": false, "status": "error" }
```

## Step 1 | API documentation (Swagger)

**Goal:** a browsable, always-correct description of the API.

**What we did**
1. Installed the package: `composer require darkaonline/l5-swagger`
2. Published its config: `php artisan vendor:publish --provider "L5Swagger\L5SwaggerServiceProvider"`
3. Created `app/OpenApi/OpenApiSpec.php` with the global parts: API title and version, server URL,
   the `bearerAuth` JWT scheme, and shared schemas (`User`, `Token`, `ApiResponse`) and shared
   responses (401, 403, 422, 429).
4. Documented each endpoint with `#[OA\...]` attributes on the `AuthController` methods.
5. Set `APP_URL=http://support-ticket-sla.test`. The server URL in the docs reads `APP_URL`.
6. Generated the docs: `php artisan l5-swagger:generate`

**Open the docs:** `http://support-ticket-sla.test/api/documentation`

**Why**
- API documentation is a listed bonus in the assessment.
- Docs written next to the code are less likely to go out of date.
- Attributes (not docblock comments) are supported natively by PHP 8.3 and checked by the IDE.
- Reading the server URL from `APP_URL` means the docs follow the environment, with no hard-coded host.
- Shared responses are written once, so every endpoint shows the same error shapes.

**Remember:** run `php artisan l5-swagger:generate` after changing any `#[OA\...]` attribute.

## Step 2 | Define the roles

**Goal:** one clear definition of who can exist in the system.

**What we did:** created `App\Enums\UserRole` with three cases:

| Case | Value | Label |
|---|---|---|
| `Admin` | `admin` | Administrator |
| `Agent` | `agent` | Support Agent |
| `Customer` | `customer` | Customer |

**Why**
- The assessment requires exactly these three roles.
- An enum is one source of truth: no typos from magic strings, and type-safe comparisons.
- We did **not** add a roles/permissions package. Three fixed roles don't need one, and the
  assessment says not to use components "just for the sake of it".
- Rules like "a customer sees only their own tickets" depend on the ticket itself, so they will be
  Laravel **Policies** in the ticket module.

## Step 3 | Database: the `users` table

**Goal:** store the role and the account state.

**What we did:** edited `0001_01_01_000000_create_users_table.php` and added:

| Column | Type | Purpose |
|---|---|---|
| `role` | string(20), default `customer` | Who the user is |
| `is_active` | boolean, default true | `false` = account disabled, cannot log in |
| `is_available` | boolean, default true | Agent is accepting new tickets (used by auto-assignment) |
| `last_login_at` | timestamp, nullable | When they last logged in |
| index | `(role, is_active, is_available)` | Makes "find available agents" fast |

**Why**
- We edited the original migration instead of adding a new one only because no database existed
  yet. **Once the project is deployed, every schema change must be a new migration.**
- `role` is a string, not a database `ENUM`: adding a role later needs no `ALTER TABLE`. The PHP
  enum is what prevents invalid values.
- The default is `customer`, the least-privileged role, so a missing value can never grant extra access.
- The composite index matches the exact filter auto-assignment will use, so it stays cheap with many users.

## Step 4 | The `User` model

**Goal:** make the new columns usable in code.

**What we did**
- Added the new columns to `#[Fillable]`.
- Added casts: `role` becomes a `UserRole` enum; `is_active` / `is_available` become booleans;
  `last_login_at` becomes a date.
- Added helper methods: `hasRole()`, `isAdmin()`, `isAgent()`, `isCustomer()`, `isStaff()`.
- Added query scopes: `active()`, `withRole()`, `availableAgents()`.
- Added a `role` claim to the JWT.

**Why**
- `isStaff()` (admin or agent) is the natural check for "may see internal notes" (assessment section 6).
- `availableAgents()` keeps the assignment query in one place, in sync with the index from Step 3.
- The scope is called `withRole`, not `role`, so it doesn't clash with the `role` attribute.
- The `role` claim in the token is only a convenience for the front end. The server **never trusts
  it for authorization**; it always reads the role from the database.

## Step 6 | Code layers

**Goal:** keep HTTP, business rules and data access in separate places.

| Layer | File | Job |
|---|---|---|
| Controller | `AuthController` | HTTP only: takes a request, calls the service, returns a resource |
| Service | `AuthService` | Business rules (inactive accounts, registration creates a customer) |
| Interface | `AuthInterface` | The list of data operations the service may use |
| Repository | `AuthRepository` | The only place that talks to the JWT guard and the database |
| DTOs | `LoginCredentialDTO`, `RegisterDTO`, `AuthTokenDTO` | Typed data passed between layers |
| Binding | `RepositoryServiceProvider` | Connects the interface to the repository |

**Why**
- Rules become easy to test and swap (the assessment grades *separation of concerns*).
- The controller no longer calls `auth()` directly. If the token system changes, only the repository changes.
- `AuthTokenDTO` carries the token, its lifetime and the user together, so resources don't read
  global `auth()` state.

## Step 7 | Login

**Goal:** `POST /api/auth/login` returns a token only for valid, active users.

**What happens, in order**
1. `validateCredentials()` checks email and password **without** creating a token.
2. Wrong credentials: throw `InvalidCredentialsException` (becomes **401**).
3. Account has `is_active = false`: throw `AccountInactiveException` (becomes **403**).
4. Otherwise: save `last_login_at`, create the token, return it with the user.

**Why**
- The inactive check happens **before** a token exists. Otherwise a disabled user would briefly hold a valid token.
- Unknown email and wrong password give the **same message**, so the API never reveals which emails are registered.
- The old code threw `UserNotFoundException`, a class that didn't exist, which caused a 500. That is fixed.

---

## Step 8 | Registration

**Goal:** customers can sign up, and only as customers.

**What we did**
- `POST /api/auth/register` takes `name`, `email` (unique), `password` (min 8) and `password_confirmation`.
- The service **always creates a customer**. A `role` sent in the request is ignored (covered by a test).

**Why:** letting the client pick its own role would be privilege escalation. Admin and agent
accounts will be created by administrators.

### What if a deactivated user registers with the same email?

| | |
|---|---|
| Result | `422` with `errors.email = ["The email has already been taken."]` |
| Token issued? | No |
| New account created? | No. The original stays deactivated |

**Why:** the `unique:users,email` rule only looks at whether the email exists, not at `is_active`.
A deactivated account is *disabled*, not *deleted*. This is intended: otherwise a banned or fired
user could escape the deactivation by signing up again. They must ask an administrator.

**Trade-off:** the message confirms the email is registered. That is normal for sign-up forms. The
rate limit in Step 11 slows down anyone probing for emails.

Test: `test_deactivated_user_cannot_re_register_with_the_same_email`.

## Step 9 | Refresh and logout

**Goal:** let users renew a token and end a session.

**What we did**
- `POST /api/auth/refresh` is **not** behind `auth:api`. A recently expired token can still be
  refreshed within `JWT_REFRESH_TTL`. After refreshing, the user is re-checked and rejected if deactivated.
- `POST /api/auth/logout` invalidates (blacklists) the token.

**Why**
- Putting `auth:api` on refresh would reject expired tokens, which is exactly when refresh is needed.
- The `is_active` re-check stops a deactivated user from renewing access forever.

## Step 10 | Middleware

**What middleware is:** code that runs **between the request arriving and the controller running**.
Each one either lets the request continue (`$next($request)`) or stops it with an error. Think of
them as security checkpoints in front of a route.

We use three. `auth:api` is built in; `active` and `role` are ours, registered in
`bootstrap/app.php`:

```php
$middleware->alias([
    'role'   => EnsureUserHasRole::class,
    'active' => EnsureUserIsActive::class,
]);
```

### 10.1 `auth:api` (built in): "who are you?"

| | |
|---|---|
| Does | Reads `Authorization: Bearer <token>`, checks signature, expiry and blacklist, loads the user |
| On failure | 401 Unauthenticated |
| Use | Any route that needs a logged-in user (`me`, `logout`) |

### 10.2 `active`: "is your account still enabled?"

File: `app/Http/Middleware/EnsureUserIsActive.php`

```php
if ($request->user() && ! $request->user()->is_active) {
    throw new AccountInactiveException();   // 403
}
return $next($request);
```

**Why it exists:** a JWT is stateless. If an admin deactivates a user, their old token stays valid
until it expires. This check runs on every request, so deactivation takes effect **immediately**.

### 10.3 `role:admin,agent`: "are you the right kind of user?"

File: `app/Http/Middleware/EnsureUserHasRole.php`

```php
$allowed = array_map(fn ($r) => UserRole::from($r), $roles);   // 'admin' -> UserRole::Admin
if (! $request->user()?->hasRole(...$allowed)) {
    throw new AuthorizationException();   // 403
}
return $next($request);
```

**How to use it** (for the next modules):

```php
Route::middleware(['auth:api', 'active', 'role:admin'])->group(...);        // admin only
Route::middleware(['auth:api', 'active', 'role:admin,agent'])->group(...);  // staff only
```

**Why it is safe**
- The role is read from the **database user**, never from the token, so editing the token can't promote anyone.
- `UserRole::from()` throws on a typo like `role:admn`, so a wrong route definition fails loudly
  instead of silently locking everyone out (or in).
- **Limit:** it only answers "is this the right *kind* of user?". "Can *this* customer see *this*
  ticket?" depends on the ticket, so that is done by Policies, not middleware.

### 10.4 Order matters

Always `auth:api` first, then `active`, then `role:...`. The last two read `$request->user()`,
which is empty until `auth:api` has run.

## Step 11 | Rate limiting: `throttle:auth`

**Goal:** stop people from hammering the public routes.

### Why it is needed

`login`, `register` and `refresh` are public, so anyone can call them:

| Attack | What it looks like |
|---|---|
| Brute force | A script tries thousands of passwords on one account |
| Credential stuffing | Leaked email/password lists from other sites are tried at speed |
| Registration spam | Bots create unlimited fake accounts |
| Load | Every login runs a deliberately slow bcrypt hash |

### Where does `throttle:auth` come from?

It has **two parts**, and neither is custom middleware:

1. **`throttle`**: a middleware alias that Laravel ships by default. It maps to
   `Illuminate\Routing\Middleware\ThrottleRequests`. We didn't write or register it.
2. **`auth`** (after the colon): the **name of a limiter we defined** with `RateLimiter::for('auth', ...)`.

So `throttle:auth` means "use the built-in throttle, with our limiter named `auth`". This `auth`
has **nothing to do** with the `auth:api` middleware. It's just a label; you could rename it
`auth-attempts` as long as both places match.

### `throttle:auth` is not a replacement for `auth:api`

They answer different questions and are used on different routes:

| | `auth:api` | `throttle:auth` |
|---|---|---|
| Question | Who are you? | How often are you calling? |
| Needs a token | Yes | No |
| Failure | 401 | 429 |
| Used on | `me`, `logout` | `register`, `login`, `refresh` |

`login` and `register` can't use `auth:api` because the caller has no token yet. That is why they
need a rate limit instead. `me` and `logout` need a valid token, so they aren't an anonymous target.

### How it is defined (`AppServiceProvider::boot`)

```php
RateLimiter::for('auth', fn (Request $request) => [
    Limit::perMinute(5)->by(strtolower((string) $request->input('email')).'|'.$request->ip()),
    Limit::perMinute(20)->by($request->ip()),
]);
```

A request must pass **both** limits:

| Limit | Counted per | Stops |
|---|---|---|
| 5 per minute | email + IP | Guessing one account's password from one machine |
| 20 per minute | IP only | One machine trying many different emails |

- `strtolower` makes `A@x.com` and `a@x.com` share a counter, so changing the case doesn't reset it.
- Counters live in the cache (`CACHE_STORE`).

### What the client sees after the limit

```
HTTP 429
Retry-After: 42
{"data":null,"message":"Too many requests. Please try again later.","errors":[],"success":false,"status":"error"}
```

`Retry-After` (seconds) tells the client when to try again.

**Deployment note:** behind a proxy or load balancer, `$request->ip()` is the proxy's address unless
trusted proxies are configured. That would put all users in one bucket, so configure them before deploying.

Test: `test_login_is_rate_limited` (5 wrong attempts, the 6th returns 429).

## Step 13 | Error handling: `ApiExceptionRenderer`

**Goal:** every error comes back in the same JSON format as a success response.

**What we did:** created `App\Exceptions\ApiExceptionRenderer`, the single place that turns
exceptions into responses. `bootstrap/app.php` only needs one line:

```php
->withExceptions(function (Exceptions $exceptions): void {
    (new ApiExceptionRenderer)->register($exceptions);
})
```

**Why**
- Before, the error format was spread over four places. Now you change it in one file.
- `InvalidCredentialsException` and `AccountInactiveException` are plain classes with no HTTP code.
  The service says *what* went wrong; the renderer decides *how it looks* to the client.
- To support a new error later (say `TicketAlreadyAssignedException` returning 409), throw it in the
  service and add one `render()` line in the renderer.

### What each exception becomes

| Exception | Status | Comes from |
|---|---|---|
| `ValidationException` | 422 | A form request failing validation |
| `InvalidCredentialsException` | 401 | `AuthService::login()` (wrong email or password) |
| `AuthenticationException`, `JWTException` | 401 | `auth:api` (missing, invalid, expired or blacklisted token) |
| `AccountInactiveException` | 403 | `AuthService` and the `active` middleware |
| `AuthorizationException`, `AccessDeniedHttpException` | 403 | The `role` middleware, and policies later |
| `ThrottleRequestsException` | 429 | `throttle:auth` (keeps the `Retry-After` header) |

Message texts live in `lang/en/apiresponse.php`.

### How the class works, part by part

| Part | What it does |
|---|---|
| `use ApiResponses` | Reuses the same response builders as successful responses, so the JSON shape can't drift |
| `register(Exceptions $exceptions)` | Called once at boot; attaches all our rules to Laravel's exception handler |
| `shouldRenderJsonWhen(...)` | Makes API requests always get JSON errors, never an HTML error page |
| `$exceptions->render(fn (SomeException $e, Request $request) => ...)` | Registers one handler. Laravel reads the **type hint** of the first parameter and runs the handler only for that exception class |
| `A\|B` in a type hint | One handler serves two exception classes (for example `AuthenticationException\|JWTException`) |
| `isApi($request)` | True when the path starts with `api/` **or** the client sent `Accept: application/json` |
| `when($request, $respond)` | For API requests, builds and returns the JSON error. Otherwise returns `null` |
| Returning `null` | Tells Laravel "I'm not handling this", so it falls back to its normal pages for browser routes |
| `->withHeaders($e->getHeaders())` | Copies `Retry-After` and `X-RateLimit-*` onto the 429 response |

**Order:** Laravel uses the first handler whose type matches. Our exceptions don't overlap with
Laravel's, so today order is only a convention. When adding more, keep specific handlers above general ones.

### Example: login with a wrong password

```
POST /api/auth/login
 -> AuthService::login(): validateCredentials() returns null
 -> throws InvalidCredentialsException
 -> Laravel finds the handler whose type hint matches
 -> isApi() is true -> unauthenticatedResponse('Invalid email or password.')
 <- 401 {"data":null,"message":"Invalid email or password.","errors":[],"success":false,"status":"error"}
```

## Step 14 | Bug fix: `Route [login] not defined`

**Symptom:** opening `GET /api/auth/me` without a token in a browser (or Swagger "Try it out"
without a token) returned **500** `RouteNotFoundException: Route [login] not defined`, not a 401.

**Cause:** when `auth:api` fails on a request that doesn't send `Accept: application/json`, Laravel
builds a redirect to `route('login')`. This app is API-only and has no web route named `login`, so
building the redirect crashed before our error handler could answer.

**Fix** (`bootstrap/app.php`):

```php
$middleware->redirectGuestsTo(fn () => null);
```

Guests are never redirected. `ApiExceptionRenderer` now returns the 401 JSON for every `api/*`
request, whatever the `Accept` header says.

**Test:** `test_unauthenticated_request_without_json_accept_header_gets_401_not_a_redirect`.

**Using protected endpoints in Swagger UI**
1. Run `POST /api/auth/login` and copy `data.access_token`.
2. Click **Authorize** and paste the token (Swagger adds `Bearer ` for you).
3. Now `me` and `logout` work. Without a token you get a normal 401.

## Step 15 | Tests

File: `tests/Feature/Auth/AuthTest.php`: **15 tests** (17 in the whole suite, all passing).

| Area | What is checked |
|---|---|
| Login | Success and role in response; wrong password; inactive user; validation; rate limit |
| Registration | Always a customer (sent role ignored); duplicate email; deactivated user can't re-register |
| Tokens | `me` works with a token; 401 without a token; 401 (not a redirect) without the JSON header |
| Deactivation | An old token of a deactivated user is rejected |
| Session | Logout invalidates the token; refresh returns a new token |
| Roles | `role:admin` blocks a customer and lets an admin through |

**Why these:** privilege escalation, deactivated accounts, the token lifecycle and role gating are
the security-critical paths the assessment's *Security and Authorization* criterion looks at.

Tests use in-memory SQLite (see `phpunit.xml`), so they never touch your MySQL data.

## Step 16 | Run it yourself

