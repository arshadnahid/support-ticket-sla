## Big picture

Three ways to give a ticket an assignee, **one rule underneath**: the ticket row is locked and
re-read before anything is decided (how and why: [5.concurrent-assignment.md](5.concurrent-assignment.md)).

re-read before anything is decided.

```
 Admin  ──POST /assign───────┐
 Agent  ──POST /accept───────┼──► TicketAssignmentService
 Queue  ──AutoAssignTicket───┘        BEGIN
                                      SELECT ticket ... FOR UPDATE      <- the lock
                                      still assignable? still unassigned?
                                      UPDATE tickets SET assigned_to ...
                                      fire TicketAssigned (after commit)
                                      COMMIT
```

## Flows | What happens to a ticket

Read this first: it shows the whole journey. The steps after it explain each part.

### Words used in this document

| Term | Meaning |
|---|---|
| **Unassigned ticket** | An active ticket (open, in progress, waiting for customer) with `assigned_to = null`. The **unassigned queue** is all of these. Agents can see this queue; only the *accept* action (or an admin, or the queue job) can take a ticket out of it |
| **Assigned ticket** | Has an agent in `assigned_to`. Only that agent (and admins) can work it |
| **Accept** | An agent takes an *unassigned* ticket for themselves. It only works while nobody else has it |

Section 5 of the assessment is about the **unassigned queue**: two agents accept the *same unassigned
ticket* at the same time. See [5.concurrent-assignment.md](5.concurrent-assignment.md) for that case.

### Flow 1 | A new ticket: from creation to an assignee

```
Customer: POST /api/tickets
   |
   v
Ticket saved                status = open, assigned_to = null      -> it is now in the UNASSIGNED QUEUE
Event TicketCreated fired
   |
   v
TICKET_AUTO_ASSIGN = true ?
   |-- no ------------------------------------------------> stays unassigned until Flow 3 or Flow 4
   |
   yes
   v
Job AutoAssignTicket queued          (customer already got their 201 response)
   |
   v   ... a queue worker picks it up (usually within a second or two) ...
   |
Is there at least one agent who is ACTIVE and AVAILABLE ?
   |-- no ------------------------------------------------> stays unassigned; the sweep retries (Flow 2)
   |
   yes
   v
Pick the agent with the FEWEST active tickets
(tie: the one who has waited longest for a ticket; last tie: lowest id)
   |
   v
ASSIGNED   assigned_to, assigned_at saved, agent's last_assigned_at updated
Event TicketAssigned fired (method = auto)
```

### Flow 2 | Nobody was available: the scheduled sweep

```
Every minute (scheduler):  php artisan tickets:assign-unassigned
   |
   v
Find active tickets with no agent  (critical first, then oldest)  -> up to 200
   |
   v
Queue one AutoAssignTicket job per ticket          (the command assigns nothing itself)
   |
   v
Worker runs each job -> same logic as Flow 1
   |-- an agent is available now  -> ASSIGNED
   |-- still nobody               -> stays in the queue, tried again next minute
```

### Flow 3 | Manual assignment by an admin

```
Admin: POST /api/tickets/{number}/assign   { "agent_id": 3 }
   |
   v
Is the user an admin?                           no  -> 403
Is agent_id an ACTIVE agent?                    no  -> 422   (availability is not checked)
   |
   v
BEGIN; lock the ticket row
   |-- ticket resolved or closed ?              yes -> 409
   |-- already assigned to this same agent ?    yes -> 200, nothing changes, no event
   v
Save assignee (reassigning is allowed)  ->  COMMIT
Event TicketAssigned (method = manual, previousAssigneeId = old agent or null)
```

### Flow 4 | An agent accepts a ticket from the unassigned queue

```
Agent: POST /api/tickets/{number}/accept
   |
   v
Is the user an agent?                           no  -> 403
   |
   v
BEGIN; lock the ticket row (SELECT ... FOR UPDATE)
   |-- ticket resolved or closed ?              yes -> 409
   |-- assigned to ME already ?                 yes -> 200 (pressed twice: harmless, no new event)
   |-- assigned to SOMEONE ELSE ?               yes -> 409 "already assigned to another agent"
   v   (still unassigned)
Save assignee = me  ->  COMMIT
Event TicketAssigned (method = accepted)         -> 200 "Ticket accepted"
```

### Flow 5 | After the ticket has an assignee

```
                     assigned agent                                  customer
UNASSIGNED --assign/accept/auto--> ASSIGNED (status still "open")
                                      |
                                      |  agent: POST /status {in_progress}
                                      v
                                 IN PROGRESS <------------------+
                                      |  |                       | agent: back to in_progress
                      agent: waiting  |  |  agent: resolve       |
                                      v  v                       |
                         WAITING FOR CUSTOMER      RESOLVED -----+   (reopen: resolved -> in_progress)
                                      |                 |
                                      +------> CLOSED <-+    <---- customer may close their own ticket
                                               (final)

 At any time while the ticket is active, an admin may reassign it (Flow 3).
 Resolved or closed tickets can no longer be assigned or accepted.
```

### The journey at a glance

| # | Moment | Who or what | Ticket state | Event fired |
|---|---|---|---|---|
| 1 | Customer creates | Customer | open, unassigned | `TicketCreated` |
| 2a | Automatic path | Queue job (Flow 1 or 2) | open, **assigned** | `TicketAssigned` (auto) |
| 2b | Manual path | Admin (Flow 3) | open, **assigned** | `TicketAssigned` (manual) |
| 2c | Pick-up path | Agent (Flow 4) | open, **assigned** | `TicketAssigned` (accepted) |
| 3 | Work starts | Assigned agent | in progress | `TicketStatusChanged` |
| 4 | Fix delivered | Assigned agent | resolved | `TicketStatusChanged` |
| 5 | Finished | Agent, admin or the customer | closed | `TicketStatusChanged` |

Steps 2a, 2b and 2c are alternatives: a ticket leaves the unassigned queue by exactly one of them
(and an admin can still reassign it afterwards).

**With automatic assignment on, the unassigned queue is usually short.** Most tickets get an agent
within seconds. What stays in the queue is tickets nobody was available for, or every ticket when
`TICKET_AUTO_ASSIGN=false`. That is when agents accepting tickets themselves (Flows 4 and 5) matters most.

## Step 1 | Decisions at a glance

| Question | Decision |
|---|---|
| Manual assignment | An **admin** assigns or reassigns a ticket to any active agent |
| Agents taking work | An **agent** can **accept** a ticket from the unassigned queue |
| Two agents accept at once | `SELECT ... FOR UPDATE` on the ticket row inside a transaction. One wins, the other gets **409** |
| Automatic strategy | **Least workload**; ties go to whoever has waited longest (round-robin among equals) |
| Who counts as a candidate | Role agent, account active, **marked available** |
| Where automatic assignment runs | A **queued job** (never inside the request) |
| Scheduler needed? | **Yes, one small command** (every minute) that re-queues tickets still waiting. The assigning itself is done by the queue |

## Step 2 | Database

One migration (`add_assignment_columns`).

| Column | Table | Why |
|---|---|---|
| `assigned_at` | `tickets` | When the current assignee got it. Shown in the API; useful for SLA and history later |
| `last_assigned_at` | `users` | Tie-break for automatic assignment: among equally busy agents, the one who received a ticket longest ago goes first (never-assigned agents go first) |

No new index: the sweep query (`assigned_to IS NULL` + active status) uses the existing
`(assigned_to, status)` index from the Ticket module, and the workload count is a single grouped
query over the same index.

---

## Step 3 | Permissions

| Action | Admin | Agent | Customer |
|---|---|---|---|
| `assign` (give to an agent) | yes | no | no |
| `accept` (take for yourself) | no (use assign) | yes | no |

**Why `accept` does not check "is it still unassigned?" in the policy.** That answer has to come
from the *locked* row inside the service. If the policy checked it, an agent who lost the race
could be told **403 Forbidden** (confusing) instead of **409 "already assigned"** (accurate).
So the policy only asks "are you an agent?" and the service decides the rest.

**Trade-off:** an agent can learn that a ticket they can't view is already taken (409 rather than
403/404). The message never says who has it.

## Step 4 | Manual assignment by an admin

`POST /api/tickets/{number}/assign` with `{ "agent_id": 3 }`.

| Rule | Behaviour |
|---|---|
| `agent_id` must be an **active agent** | Otherwise **422** (a customer, an admin, a deactivated agent or an unknown id are all rejected) |
| Availability is **not** required | An admin may hand a ticket to an agent marked unavailable. "Available" only steers *automatic* assignment |
| Reassigning | Allowed. The old assignee is recorded in the event (`previousAssigneeId`) |
| Assigning to the current assignee | Succeeds, changes nothing, fires no event |
| Resolved or closed ticket | **409** (`A closed ticket cannot be assigned.`) |

Once assigned, the agent can edit and resolve the ticket under the normal rules of
[2.tickets.md](2.tickets.md) (Step 6 of that document).

## Step 5 | Automatic assignment

### The strategy: least workload, then longest wait

`LeastWorkloadStrategy` chooses among agents who are **active and available**:

1. the agent with the **fewest active tickets** (open, in progress, waiting for customer);
2. on a tie, the agent who **went longest without receiving a ticket** (`last_assigned_at`, never-assigned first). Equal agents therefore take turns, like round-robin;
3. on a further tie, the lowest id (so the result is deterministic).

**Why this rule**
- It keeps work even without anyone maintaining a rotation list.
- It reacts to reality: an agent who is swamped, or who finishes tickets, changes their share on the next ticket.
- It respects availability (section 4 lists "agent availability" as an example input).
- It needs no setup per category or skill.

The rule sits behind an interface (`AssignmentStrategy`), bound in `AppServiceProvider`. Changing it
(round-robin only, by category, by skill, a cap per agent) means writing one class and changing one binding.

### How it runs

```
POST /api/tickets (create)
   -> TicketCreated event                      (after the transaction commits)
   -> QueueAutoAssignment listener             dispatches AutoAssignTicket(ticketId)
   <- 201 returned to the customer             does NOT wait for any of what follows

   ...later, on a queue worker...
   AutoAssignTicket::handle
   -> TicketAssignmentService::autoAssign
        BEGIN
        lock ticket row; stop if already taken or finished
        lock available agent rows (ordered by id)
        count each agent's active tickets (one grouped query)
        strategy picks one; write assignment; fire TicketAssigned
        COMMIT
```

**Why a queued job:** creating a ticket should not wait for (or fail because of) assignment work,
and a busy moment only delays the job. The listener is found automatically by Laravel (it lives in
`app/Listeners` and type-hints `TicketCreated`).

**Why the agents are locked too:** if two jobs ran together, both could read the same workload
numbers and pick the same agent. Locking the agent rows makes the jobs take turns, so each sees
the previous one's result. The counts are read *after* the locks are held, so they are current.

**The job is `ShouldBeUnique` per ticket:** the listener and the sweep may both queue the same
ticket; only one copy waits at a time. It retries 3 times (10 s, then 60 s apart).

**No agent available is not an error.** The job ends normally and the ticket stays in the queue
for agents to accept or for the next sweep (below).

## Step 6 | Do we need a scheduler or command?

**Yes, one small one. The queue alone is not enough.**

| Situation | Handled by |
|---|---|
| A new ticket arrives and agents are available | Listener queues the job. **No scheduler needed** |
| A new ticket arrives and **every agent is unavailable** | Job finds nobody and ends. **Nothing would ever retry it** |
| An agent later becomes available, or a new agent is added | Nothing notices. Tickets would wait until someone accepts them |
| A job failed all 3 attempts, or the queue was down | Ticket stays unassigned |

So a **sweep** re-offers waiting tickets:

```
php artisan tickets:assign-unassigned          (scheduled every minute)
```

- Finds active, unassigned tickets (most urgent first: critical before low, then oldest), up to
  `TICKET_AUTO_ASSIGN_BATCH` (default 200).
- **Queues one `AutoAssignTicket` job per ticket.** It assigns nothing itself, so all assignment
  logic and locking stays in one place.
- Registered in `routes/console.php` with `everyMinute()`, `withoutOverlapping()` and `onOneServer()`.
- Does nothing when `TICKET_AUTO_ASSIGN=false`.
- Safe to run often: unique jobs mean an already-queued ticket is not queued twice.

**What must be running**

| Process | Command | Needed for |
|---|---|---|
| Queue worker | `php artisan queue:work` | Any automatic assignment |
| Scheduler | `php artisan schedule:work` (dev) or a cron/Task Scheduler entry running `php artisan schedule:run` every minute (production) | The sweep |

If no worker is running, new tickets simply stay unassigned (nothing is lost; the jobs wait in the
`jobs` table). Admins and agents can still assign by hand. This is the same scheduler and queue
the SLA escalation and email notifications will use later.

## Step 7 | Events

`TicketAssigned` is fired after commit, for all three ways:

| Field | Meaning |
|---|---|
| `ticket`, `assignee` | What and to whom |
| `method` | `manual`, `accepted` or `auto` |
| `actor` | The admin or agent; `null` for automatic (the system) |
| `previousAssigneeId` | Set when a ticket was reassigned |

No listener yet besides the auto-assign trigger on `TicketCreated`. Later modules attach
notifications ("Ticket assigned", section 11) and the activity entry ("Assigned to Agent B at 10:05",
section 15) here without touching assignment code.

## Step 8 | Endpoints and configuration

| Method and path | Who | Success | Failures |
|---|---|---|---|
| `POST /api/tickets/{number}/assign` `{agent_id}` | Admin | 200 | 403, 404, 409 (finished), 422 (not an active agent) |
| `POST /api/tickets/{number}/accept` | Agent | 200 | 403, 404, **409** (taken by another agent, or finished) |

`.env` settings (`config/tickets.php`):

| Variable | Default | Meaning |
|---|---|---|
| `TICKET_AUTO_ASSIGN` | `true` | `false` = assign by hand only (no listener job, sweep does nothing) |
| `TICKET_AUTO_ASSIGN_BATCH` | `200` | Max tickets the sweep queues per run |

Swagger and Bruno (`assign ticket (admin)`, `accept ticket (agent)`) are updated.

## Step 9 | Tests and how it was checked

`TicketAssignmentTest` has 16 tests. The concurrency ones are listed in [5.concurrent-assignment.md](5.concurrent-assignment.md#step-3--tests-and-how-it-was-checked).

| Covered | Tests |
|---|---|
| Admin assigns; event data (method, actor); `assigned_at` and `last_assigned_at` saved | yes |
| Reassign records the previous agent; same agent again is a no-op | yes |
| Unavailable agent can be assigned by an admin | yes |
| Invalid `agent_id` (customer, admin, deactivated agent, unknown, missing) | yes |
| Agent and customer cannot assign; guests get 401 | yes |
| Resolved or closed tickets cannot be assigned or accepted | yes |
| Assigned agent can then resolve the ticket | yes |
| Accepting twice is harmless (one event); unavailable agent may accept; admin and customer cannot | yes |
| **Automatic assignment** | **Not unit-tested, by request** |

The automated tests run with `TICKET_AUTO_ASSIGN=false` (in `phpunit.xml`) so existing ticket tests
are not affected by background assignment.

**Checks beyond the test suite (real MySQL and queue)**

1. **Automatic assignment, by hand:**
   - Sweep: 3 waiting tickets were queued, the command assigned **none itself**, a worker then assigned all 3. The agent marked unavailable received none.
   - New ticket through the API: the response came back with no assignee and a job waiting; after the worker ran it went to the agent with the lower workload (11 vs 12 active tickets).
   - Everyone unavailable: the job finished without failure (0 failed jobs) and the ticket stayed unassigned.
   - An agent became available again: the next sweep assigned it.

## Step 10 | Decisions, assumptions and limits

1. **Automatic assignment has no automated tests**, as requested. It was verified manually (Step 9).
   `LeastWorkloadStrategy` is a pure function of its input and would be the easiest first test to add.
2. **No category or skill matching.** The assessment lists category as an example; the strategy
   interface is where it would go.
3. **No cap per agent.** One very busy agent is simply not chosen while others have less, but there
   is no hard limit.
4. **No "unassign / release" endpoint** and **no endpoint to toggle an agent's availability** yet
   (`is_available` is set in the database or by a future admin module). An admin can reassign to fix a wrong assignment.
5. **Automatic assignments queue up behind each other** (they lock the available agents). That keeps
   workload numbers correct and is fine for a support desk; very high ticket volume would need a different approach.
6. **Needs a running queue worker.** Without one, auto-assignment waits (nothing is lost).
7. **Assigning does not change the status.** A ticket stays `open` until the agent moves it to `in_progress`.
8. **The 409 on accept reveals a ticket is taken** to an agent who can't view it (Step 3).
9. **Uniqueness of the job uses the cache** (`CACHE_STORE=database`, which has the lock table). If you
   change the cache driver, use one that supports locks.

## Step 11 | Run it yourself

```bash
php artisan migrate                          # adds assigned_at, last_assigned_at
php artisan queue:work                       # terminal 1: automatic assignment
php artisan schedule:work                    # terminal 2: runs the sweep every minute
php artisan tickets:assign-unassigned        # or run the sweep once by hand
php artisan test
```

1. Log in as `customer1@example.com` and create a ticket. Its `assigned_to` is `null` in the response.
2. Watch the queue worker assign it, then `GET /api/tickets/{number}` to see the agent.
3. To try the accept race by hand: set `TICKET_AUTO_ASSIGN=false`, create a ticket, then call
   `POST /accept` as `agent1@example.com` and again as `agent2@example.com`. The second gets 409.
4. To try manual assignment: log in as `admin@example.com` and `POST /assign` with `{"agent_id": 3}`
   (agent ids in the demo data: 3, 4, 5).
