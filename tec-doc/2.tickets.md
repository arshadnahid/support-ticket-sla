## Big picture

```
POST /api/tickets
  -> auth:api + active                      who are you, is your account enabled?
  -> StoreTicketRequest                     is the input valid?
  -> TicketController::store
       Gate::authorize('create')            TicketPolicy: may this role do this?
  -> TicketService::create                  one DB transaction:
       TicketNumberGenerator::next()          lock + increment the year counter -> TKT-2026-000031
       TicketRepository::create()             insert the ticket
       TicketCreated event                    (listeners come from later modules)
  <- 201 TicketResource
```

## Step 1 | Scope and plan

| In this module | Left for later (but prepared) |
|---|---|
| Create / view / update ticket | Assignment, auto-assignment, concurrent accept (4, 5) |
| Resolve / close, status flow | Conversation, internal notes (6) |
| Active list and resolved/closed list, pagination | Attachments (7) |
| Unique ticket numbers `TKT-YYYY-NNNNNN` | SLA deadline, business hours, escalation (8 to 10) |
| Roles and permissions (policy) | Notifications (11), search and filters (12) |

**Why this order:** permissions and ticket identity touch everything else. Getting them right first
means later modules reuse `TicketPolicy`, `Ticket::visibleTo()` and the events instead of reinventing them.

## Step 2 | Enums: priority, status, list scope

| Enum | Values | Notes |
|---|---|---|
| `TicketPriority` | low, medium, high, critical | `weight()` for ordering; the SLA module will map each to a resolution time |
| `TicketStatus` | open, in_progress, waiting_for_customer, resolved, closed | Knows its own `allowedTransitions()`; `active()` and `finished()` groups |
| `TicketListScope` | all, active, finished | Which list the repository should build |

**Why enums, not DB `ENUM` columns:** the database stores plain strings, so adding a status later
needs no `ALTER TABLE`. The PHP enum is the single place that defines valid values and transitions.

**Why the transition rules live in `TicketStatus`:** "can a closed ticket reopen?" is a business
rule. Keeping it on the enum means the controller, service and tests all read the same answer.

## Step 3 | Database

Three new migrations (run `php artisan migrate`).

### `categories`

| Column | Notes |
|---|---|
| `name` (unique), `slug` (unique) | `slug` is the stable identifier |
| `is_active` | Inactive categories stay on old tickets but can't be chosen for new ones |

### `ticket_sequences`

| Column | Notes |
|---|---|
| `year` (primary key) | One row per year |
| `last_number` | Last number handed out that year (see Step 5) |

### `tickets`

| Column | Notes |
|---|---|
| `number` (unique) | Public ID, `TKT-2026-000001`. Used in URLs |
| `subject`, `description` | |
| `priority`, `status` | Strings backed by the enums |
| `category_id`, `created_by`, `assigned_to` | Foreign keys. `assigned_to` is nullable (unassigned queue) |
| `due_at` | SLA deadline. Nullable, filled in by the SLA module |
| `resolved_at`, `closed_at` | Set by the status flow |

**Foreign key rules:** `category_id` and `created_by` use `restrictOnDelete` (you can't delete a
user or category that has tickets, which protects history). `assigned_to` uses `nullOnDelete`
(deleting an agent returns their tickets to the unassigned queue).

### Indexes: each one exists for a specific query

| Index | Query it serves |
|---|---|
| `number` (unique) | Looking up a ticket by its public number; guarantees no duplicates |
| `(created_by, status)` | A customer's own tickets, active vs finished |
| `(assigned_to, status)` | An agent's queue; workload counts for auto-assignment |
| `(status, due_at)` | The active list ordered by deadline; the SLA escalation scan ("active and due soon") |
| `(status, priority)` | Dashboard counts by priority |
| `created_at` | Newest-first ordering and date filters |

**Why not index everything:** every index slows inserts and takes space. These five match the
queries the assessment asks for. Free-text search (module 12) will need its own approach later.

## Step 4 | Models

- **`Ticket`**: casts `priority` and `status` to enums; relations `category`, `creator`, `assignee`.
  `getRouteKeyName()` returns `number`, so URLs are `/api/tickets/TKT-2026-000001`.
- **`Category`**: `active()` scope.

Query scopes on `Ticket`:

| Scope | Meaning |
|---|---|
| `visibleTo($user)` | Only the tickets this user may see (the permission rule as a query, see Step 6) |
| `active()` | open, in_progress, waiting_for_customer |
| `finished()` | resolved, closed |

**Why the ticket number is the route key:** sequential ids (`/tickets/7`) are guessable. The number
is still sequential, but it is the identifier users already see and quote, and it never leaks how
many tickets exist in the internal id space.

## Step 5 | Ticket ID generation

**Goal:** `TKT-2026-000001`: unique, no gaps, still correct after millions of tickets.

**Format:** `prefix` + `-` + `year` + `-` + counter padded to 6 digits. Prefix and padding come
from `config/tickets.php` (`TICKET_NUMBER_PREFIX`, `TICKET_NUMBER_PADDING`). The counter restarts
each year. After 999,999 the number simply gets longer (`TKT-2026-1000000`); nothing breaks.

**How it works** (`TicketNumberGenerator`)

1. One counter row per year in `ticket_sequences`.
2. `UPDATE ... SET last_number = last_number + 1` increments it. The UPDATE locks the row, so a
   second request arriving at the same moment waits for the first to commit.
3. The new value is read back and formatted.
4. It runs **inside the same transaction as the ticket insert**. If the insert fails, the counter
   rolls back too, so numbers have no gaps.
5. `tickets.number` has a UNIQUE index as a last line of defence.

**Why not `MAX(id)+1` or a random code:** `MAX+1` produces duplicates under concurrency. A
database auto-increment can't be reset per year and loses numbers when a transaction rolls back.

**Trade-off:** ticket creation is serialised for a few milliseconds (the lock is held until the
transaction commits). That is fine for a support desk. A much higher write rate would use
pre-allocated blocks of numbers.

### A bug found by load-testing, and its fix

The first version did "insert the year's row if missing, then `SELECT ... FOR UPDATE`, then update".
Unit tests on SQLite passed. But with **8 parallel PHP processes on MySQL, 151 of 200 requests failed
with `Deadlock found when trying to get lock`** (the numbers that did get created were still unique).

**Cause:** inserting a row that already exists takes a *shared* lock; the following `FOR UPDATE`
needs an *exclusive* lock. Two requests each holding the shared lock and waiting to upgrade
deadlock each other.

**Fix:** increment **first** with an UPDATE, which takes the exclusive lock immediately, and only insert the
row when the UPDATE touched nothing (first ticket of the year). The transactions also retry on a
deadlock (`attempts: 3`).

**Result after the fix (real MySQL, 8 parallel processes):** 200 of 200 created, 230 distinct
numbers, counter exactly 230. A second run starting with an empty counter table (first-ticket race)
also gave 80 unique numbers with no errors.

**Lesson recorded:** test locking code against the real database engine with parallel workers.
SQLite ignores row locks, so it cannot reveal this kind of bug.

## Step 6 | Roles and permissions

**Goal (assessment section 3):** customers see only their tickets; agents do only what they are
allowed to; admins have administrative access; everything enforced on the server.

**Design:** *role* decides the kind of access, *ownership or assignment* decides whether it applies
to **this** ticket. Implemented as a Laravel Policy (`TicketPolicy`). No permissions package: three
roles with ownership rules don't need a database of permissions.

### Permission matrix

| Action | Admin | Support agent | Customer |
|---|---|---|---|
| List tickets | all | assigned to them + unassigned queue | own tickets |
| View a ticket | any | assigned to them, or unassigned | own |
| Create a ticket | yes | yes | yes |
| Update a ticket | any (not closed) | assigned to them (not closed) | own, only while status is `open` |
| Change `priority` | yes | assigned to them | **never** (validation rejects it) |
| Change status | any | assigned to them | own, **only to `closed`** |
| See staff email addresses | yes | yes | no |

Closed tickets can't be edited by anyone.

### Where each rule is enforced

| Layer | What it does |
|---|---|
| `auth:api` + `active` middleware | You must be logged in and enabled |
| `TicketPolicy` via `Gate::authorize()` in the controller | Per-ticket rule for view / update / status. Refusal = **403** |
| `Ticket::visibleTo($user)` scope | Same rule for lists, applied in the SQL query so hidden tickets are never loaded |
| `UpdateTicketRequest` | Customers get a validation error if they send `priority` |
| `UserSummaryResource` | Emails of creator/assignee only shown to staff |

**Why two copies of the rule (policy and scope):** a policy checks one loaded ticket; a list needs
the same rule as a `WHERE` clause, otherwise you would load everything and filter in PHP. Both are
in the code next to a "keep in sync" comment and both are covered by tests.

**Why agents can see the unassigned queue:** the assessment says two agents may try to accept the
same unassigned ticket (section 5), so agents must be able to see unassigned tickets. They can *view*
them but not edit or resolve them until assigned (module 4 adds the accept action).

**Why 403 and not 404 for someone else's ticket:** the policy answer is explicit and testable.
Guests get **401 before any lookup**, so an anonymous caller can't use 404-vs-403 to find which
ticket numbers exist.

**Why `role:` middleware isn't used here:** route-level role checks only answer "what kind of user".
Ticket rules depend on the individual ticket, so they belong in the policy.

## Step 7 | Service, repository and events

Same layering as the Auth module (see [1.auth.md](1.auth.md), Step 6).

| Piece | Job |
|---|---|
| `TicketController` | HTTP only: validate, authorize, call the service, return a resource |
| `TicketService` | Business rules, transactions, events |
| `TicketNumberGenerator` | Ticket numbers (Step 5) |
| `TicketInterface` / `TicketRepository` | All queries |
| `CategoryInterface` / `CategoryRepository` | Category list (no service: nothing to decide) |
| `CreateTicketDTO`, `UpdateTicketDTO` | Typed input passed to the service |

### What the service does

**`create`**: one transaction: generate number, insert ticket with `status = open` and
`created_by = the logged-in user`. The client can never set status, owner, assignee or number
(there is a test that sends them and checks they are ignored).

**`update`**: inside a transaction, re-reads the ticket **with a row lock** (`SELECT ... FOR UPDATE`),
works out which fields really changed, and saves only those. Nothing changed means no save and no event.

**`changeStatus`**: inside a transaction, re-reads the locked ticket, checks the move is allowed
(Step 10), saves the new status and timestamps.

**Why lock the row on update and status change:** the ticket loaded by route model binding can be
stale by the time we write. Without the lock, two agents could both "resolve" the same ticket, or
one edit could silently overwrite another. The same technique will be reused for concurrent assignment (module 5).

### Events

Dispatched **after the transaction commits** (`ShouldDispatchAfterCommit`), so a listener never sees
a rolled-back ticket.

| Event | Carries | Fired when |
|---|---|---|
| `TicketCreated` | ticket, actor | A ticket is created |
| `TicketUpdated` | ticket, actor, `changes` (`field => [from, to]`) | A real change was saved |
| `TicketStatusChanged` | ticket, actor, from, to | Status moved |

No listeners exist yet. **Why add events now:** the activity history ("Priority changed from Medium
to High", section 15) and notifications (section 11) are exactly "react to these events". Adding
them later then needs no change to the ticket code.

## Step 8 | Validation and resources

### Validation rules

| Request | Field | Rule |
|---|---|---|
| Create | `subject` | required, max 255 |
| | `description` | required, max 10,000 |
| | `priority` | optional, one of the four values, defaults to `medium` |
| | `category_id` | required, must exist **and be active** |
| Update | all fields | optional (`sometimes`), same limits |
| | `priority` | **prohibited for customers** |
| Status | `status` | required, a valid status value |
| Lists | `page`, `per_page` | integers; `per_page` 1 to 100 (default 15) |

**Why cap `per_page` at 100:** otherwise `?per_page=1000000` loads the whole table in one request.

### API responses

- `TicketResource` returns ids, number, subject, description, `priority` and `status` as
  `{value, label}`, category, creator, assignee, `due_at`, `resolved_at`, `closed_at`, timestamps.
- Creator and assignee use `UserSummaryResource`: only `id` and `name` (plus `email` for staff). A
  customer never receives an agent's role, last login or email.
- **N+1 prevention:** the list loads category, creator and assignee with one extra query each
  (`with(['category:id,name,slug', ...])`) and selects only the columns shown. A list of 2 or of 22
  tickets runs the **same number of queries**; a test compares a list of 2 with a list of 22.
- `whenLoaded()` in the resource means a relation that wasn't loaded is skipped instead of silently
  triggering one query per ticket.

## Step 9 | Endpoints

All need `Authorization: Bearer <token>` and an enabled account.

| Method and path | What it does | Success |
|---|---|---|
| `GET /api/categories` | Active categories (for the create form) | 200 |
| `GET /api/tickets` | Tickets I may see, newest first | 200, paginated |
| `GET /api/tickets/active` | Open, in progress, waiting; **earliest SLA deadline first**, tickets without a deadline last | 200, paginated |
| `GET /api/tickets/resolved` | Resolved and closed, most recently updated first | 200, paginated |
| `POST /api/tickets` | Create | 201 |
| `GET /api/tickets/{number}` | View | 200 |
| `PATCH /api/tickets/{number}` | Update (send only changed fields) | 200 |
| `POST /api/tickets/{number}/status` | Set a status `{ "status": "in_progress" }` | 200 |
| `POST /api/tickets/{number}/resolve` | Shortcut for status `resolved` | 200 |
| `POST /api/tickets/{number}/close` | Shortcut for status `closed` | 200 |

`active` and `resolved` are registered **before** `{ticket}` in `routes/api.php`; otherwise the
word "active" would be treated as a ticket number.

**Paginated responses** include `data` (the page) and a `pagination` block (`current_page`,
`per_page`, `total`, `last_page`, `from`, `to`, `next_page_url`, `prev_page_url`).

## Step 10 | Status flow

```
open ───────────────► in_progress ◄──────────────┐
  │                      │  ▲                     │
  │                      ▼  │                     │
  │              waiting_for_customer             │
  │                      │                        │
  └──────────────────────┼────────► resolved ──────┘  (reopen: resolved -> in_progress)
                         │             │
                         ▼             ▼
                       closed ◄────────┘      closed is final
```

| From | May move to |
|---|---|
| open | in_progress, waiting_for_customer, resolved, closed |
| in_progress | waiting_for_customer, resolved, closed |
| waiting_for_customer | in_progress, resolved, closed |
| resolved | in_progress (reopen), closed |
| closed | nothing |

Any other move returns **409 Conflict** with a message like `A ticket cannot move from "Closed" to "Open".`

| When the status becomes | Timestamps |
|---|---|
| resolved | `resolved_at = now`, `closed_at = null` |
| closed | `closed_at = now` |
| in_progress (reopen from resolved) | `resolved_at = null` |

**Who may do what** is separate and checked first (Step 6): permission (403) is decided before
validity (409).

## Step 11 | Error handling

New handlers in `ApiExceptionRenderer` (same envelope as every other error):

| Exception | Status | When |
|---|---|---|
| `InvalidTicketTransitionException` | 409 | A status move that isn't allowed |
| `NotFoundHttpException` | 404 | Unknown ticket number or unknown route (Laravel converts a missing model into this) |
| `MethodNotAllowedHttpException` | 405 | Wrong HTTP method |

Before this, an unknown ticket returned Laravel's default JSON (`{"message": "No query results..."}`),
which didn't match our `data/message/errors/success/status` format.

## Step 12 | Seed data, Swagger and Bruno

**Seeders** (`php artisan migrate:fresh --seed`)

- `CategorySeeder`: General Inquiry, Technical Issue, Billing, Account & Access, Feature Request.
- `TicketSeeder`: 30 demo tickets in all statuses. Numbers come from the real generator, so the counter stays consistent. Open tickets are partly unassigned; everything further along has an agent.
- Factories: `TicketFactory` (states `inProgress`, `resolved`, `closed`, `assignedTo`, `createdBy`, `priority`) and `CategoryFactory`.

**Swagger:** all ticket endpoints, schemas and the 403/404/409 responses are documented
(`/api/documentation`). `php artisan l5-swagger:generate` after changes.
*Gotcha found:* when one class carries both `#[OA\Schema]` and `#[OA\Parameter]` attributes,
swagger-php silently drops the schemas. So shared schemas live in `TicketSchemas` and shared
parameters/responses in `TicketComponents`.

**Bruno:** a `Ticket` folder with 10 requests. `create ticket` saves the new number into the
`ticketNumber` variable, which the other requests use. See the README for how to use Bruno.

## Step 15 | Decisions, assumptions and limits

Being explicit about what to know before relying on this:

1. **An empty list returns HTTP 404 with `success: false`.** This comes from the existing
   `ApiResponses::sendResponse()` helper, which treats an empty collection as "not found". It still
   includes the `pagination` block. I left the helper unchanged because it's shared; if clients
   should get `200` with `data: []` instead, that is a small change in that one trait.
2. **Customers choose their own priority at creation.** The assessment doesn't say otherwise, but a
   customer can mark everything Critical. If that matters, restrict `critical` to staff in `StoreTicketRequest`.
3. **Agents can only act on tickets assigned to them**, and there is no way to assign yet (module 4). Until then, only admins can work tickets; the demo data has assigned tickets for agents to try.
4. **`in_progress` / `resolved` don't require an assignee.** Reasonable once assignment exists; not enforced yet so admins aren't blocked.
5. **`due_at` stays `null`** until the SLA module, so the active list currently sorts by `id` among tickets.
6. **No category management endpoints** (create/edit/deactivate). Categories come from the seeder; `is_active` is honoured.
7. **Closed means final.** There is no reopen after close; reopening is only possible from `resolved`.
8. **Offset pagination** (`page`, `per_page`) with a total count. Fine for this size; for very large tables `cursorPaginate` would avoid the count query.

## Step 16 | Run it yourself

```bash
php artisan migrate          # adds categories, ticket_sequences, tickets
php artisan db:seed          # or: php artisan migrate:fresh --seed  (resets everything)
php artisan l5-swagger:generate
php artisan test
```

Try it in Swagger (`/api/documentation`) or Bruno (see README): log in as `customer1@example.com`
(password `12345678`), create a ticket, then log in as `admin@example.com` and move it through the statuses.
